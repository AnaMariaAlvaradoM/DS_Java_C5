01 · EL PROBLEMA

🔓 Tu API está abierta de par en par

Ya construiste VetCare: registra dueños, mascotas, agenda citas. Funciona. Pero tiene un hueco grave: ahora mismo cualquiera que conozca la dirección de tu API puede borrar todas las citas, cambiar teléfonos o eliminar dueños. No hay ninguna puerta.

En una clínica real hay una recepcionista que entra con su usuario, y un administrador con más permisos. No cualquiera toca el sistema. Hoy le pones la llave a VetCare.

Lo que lograrás hoy

Registro y login con contraseñas encriptadas · un token JWT al entrar · endpoints protegidos · roles ADMIN/USER · y un cierre pro: convertir ese feo error 500 en un 404 limpio.

Si mañana subes esta API a internet tal como está, ¿qué podría hacer un desconocido que encuentre la dirección?
▸ Ver explicación
Mucho más que ver: podría borrar todas las citas, cambiar los datos de cualquier dueño, eliminar veterinarios. Sin seguridad, la API está abierta. Hoy resuelves dos preguntas: ¿quién eres? (autenticación) y ¿qué te dejo hacer? (autorización).
02 · CONCEPTO

🧩 Autenticación vs. autorización

Estos dos términos se repetirán toda la clase y se confunden mucho. Sepáralos bien desde ya:

Autenticación: el proceso de verificar quién eres. Ocurre al hacer login: das usuario y contraseña, y el sistema confirma tu identidad.

Mostrar tu cédula en la entrada de un edificio: demuestras que eres tú.

Autorización: el proceso de decidir qué puedes hacer una vez identificado. Ocurre en cada petición protegida, según tu rol.

El color de tu escarapela dice a qué salas puedes entrar. Ya estás adentro, pero no a todo tienes acceso.

Un empleado tiene su usuario y clave correctos y entra al sistema. ¿Eso significa que puede hacer TODO adentro?
▸ Ver explicación
No. Entrar (autenticación) y tener permiso para todo (autorización) son cosas distintas. Una recepcionista entra con su clave válida, pero no debería poder borrar registros: eso es solo del administrador. Autenticado no es lo mismo que autorizado para todo.
03 · MODELO

👤 La entidad Usuario y sus roles

Para que alguien haga login, primero tiene que existir como usuario en la base. Necesitas una entidad nueva: Usuario. Es independiente, separada de Veterinario o Dueño.

Decisión de diseño

¿Por qué un Usuario aparte y no reutilizar Veterinario? Porque quien usa el software (una recepcionista, un admin) no es lo mismo que un dato del negocio (un veterinario que atiende). El Usuario es de quien entra; el Veterinario es de quien atiende. Cada cosa en su lugar.

El rol no puede ser cualquier texto ("admin", "administrador", "ADMIN"…). Para evitar errores de escritura, lo defines como un enum: una lista cerrada de valores válidos.

enum: un tipo que define un conjunto fijo y cerrado de valores posibles. Solo se puede usar uno de los que están en la lista.

Es como el menú de un restaurante: solo puedes pedir lo que está en la carta, nada por fuera.

src/main/java/com/devsenior/vetcare/model/Rol.java 
package com.devsenior.vetcare.model;

public enum Rol {
    ADMIN,
    USER
}

Ahora la entidad, con Lombok igual que las demás. El username es único (no puede haber dos iguales) y el rol se guarda como texto legible gracias a @Enumerated(EnumType.STRING).

src/main/java/com/devsenior/vetcare/model/Usuario.java 
package com.devsenior.vetcare.model;

import jakarta.persistence.*;
import lombok.AllArgsConstructor;
import lombok.Data;
import lombok.NoArgsConstructor;

@Entity
@Table(name = "usuarios")
@Data
@NoArgsConstructor
@AllArgsConstructor
public class Usuario {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String username;

    @Column(nullable = false)
    private String password;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false)
    private Rol rol;
}

Y el repositorio, que necesita buscar un usuario por su username (cuando intenta entrar). Spring Data te regala esa consulta con solo declarar el método: no escribes SQL, el nombre basta.

¿Por qué el username lo marcamos como único, pero el password no?
▸ Ver explicación
El username es tu identidad de acceso: si hubiera dos "laura", el sistema no sabría a cuál dejar entrar. La contraseña sí puede repetirse entre personas distintas (por casualidad) y además va encriptada, así que no importa. Lo único que te identifica es el username.
04 · SEGURIDAD

🔒 Nunca guardes contraseñas en texto plano

Esta es una de las lecciones de seguridad más importantes de todo el programa. Presta atención.

Si guardas la contraseña tal cual la escribió el usuario ("clave123") en la base, y algún día alguien roba la base (pasa todo el tiempo en la vida real), tendría todas las contraseñas de todos en texto legible. Un desastre.

La solución: guardas una versión encriptada e irreversible, usando un algoritmo llamado BCrypt.

BCrypt: función de hash de una sola vía para contraseñas. Permite verificar si una clave coincide, pero no permite revertir el texto guardado a la clave original.

Es como triturar un papel: puedes comparar si dos papeles se trituraron igual, pero no puedes rearmar el papel original a partir de los pedacitos.

Cuando el usuario pone clave123, en la base no se guarda clave123. Se guarda algo así:

así se ve en la base de datos 
$2a$10$N9qo8uLOickgx2ZMRZoM-eIjZAgcfl7p92ldGxad68L...

Ese texto es irreversible. En el login, BCrypt toma la clave escrita, la vuelve a triturar y compara triturado contra triturado. Nunca compara texto plano.

Si el administrador de la base abre la tabla de usuarios, ¿debería poder leer la contraseña real de sus empleados?
▸ Ver explicación
No, ni siquiera él. Una contraseña bien guardada nadie puede leerla. Se guarda encriptada con BCrypt, que es de una sola vía: se puede verificar ("¿esta clave coincide?") pero no revertir ("¿cuál era la clave?"). Así, aunque roben la base, las contraseñas siguen protegidas.
05 · CONFIGURACIÓN

⚙️ Las dependencias de seguridad y JWT

Hasta ahora tu pom.xml no sabe nada de seguridad. Necesitas agregar dos cosas: Spring Security (el sistema de seguridad) y jjwt (la librería para crear y leer tokens).

Spring Security

Enciende toda la maquinaria de seguridad. Apenas la agregas, Spring bloquea TODA la API por defecto y pide login. Eso es a propósito: es "seguro por defecto", y después tú decides qué abrir.

pom.xml · dentro de <dependencies> 
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>

Las tres dependencias de jjwt

La librería jjwt (Java JWT) viene partida en tres piezas, y entender por qué te evita errores:

jjwt-api: las interfaces, lo que escribes en tu código. jjwt-impl: la implementación real por detrás (va como runtime). jjwt-gson: convierte el contenido del token a/desde JSON (también runtime).

Es como un control remoto: tú tocas los botones (api), pero por dentro hay circuitos que hacen el trabajo (impl) y una batería que lo alimenta al usarlo (runtime).

pom.xml · dentro de <dependencies> 
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-api</artifactId>
    <version>0.12.5</version>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-impl</artifactId>
    <version>0.12.5</version>
    <scope>runtime</scope>
</dependency>
<dependency>
    <groupId>io.jsonwebtoken</groupId>
    <artifactId>jjwt-gson</artifactId>
    <version>0.12.5</version>
    <scope>runtime</scope>
</dependency>
Error clásico

Si olvidas jjwt-impl, el proyecto compila pero al arrancar truena con "no implementation found". Por eso las tres van juntas.

¿Por qué jjwt-impl y jjwt-gson van con scope runtime y jjwt-api no?
▸ Ver explicación
Porque tu código solo habla con jjwt-api (las interfaces): eso lo necesitas al escribir y compilar. La implementación y el conversor JSON solo hacen falta cuando la app está corriendo. runtime significa exactamente eso: "no la necesito para compilar, solo para ejecutar". No expones la implementación al código que escribes.
06 · REGISTRO

📝 Crear cuenta con clave encriptada

Primero, dile a Spring con qué encriptar. Defines un PasswordEncoder (el triturador de papel) como un @Bean, para usarlo en todo el proyecto.

@Bean: un objeto que Spring crea una sola vez y te presta donde lo pidas. Vive en una clase de configuración.

Es como una herramienta compartida en un taller: hay una sola, y quien la necesita la toma prestada en vez de comprar una nueva cada vez.

src/main/java/com/devsenior/vetcare/config/SecurityConfig.java 
package com.devsenior.vetcare.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;

@Configuration
public class SecurityConfig {

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }
}

Al guardar el usuario, ¿por qué llamamos a passwordEncoder.encode(...) en vez de guardar el password directo?
▸ Ver explicación
Porque el password que llega es la clave en texto plano tal como la escribió el usuario. Si la guardas así, queda legible en la base (peligrosísimo). encode(...) la tritura con BCrypt antes de guardar. Nunca, jamás, se persiste una contraseña sin encriptar. Es la regla de oro.
07 · CONCEPTO

🎫 ¿Qué es un JWT y cómo se lee?

Cuando alguien hace login correcto, ¿cómo le das una "llave" para que en las siguientes peticiones el sistema sepa que ya se identificó, sin volver a pedirle la clave cada vez?

JWT (JSON Web Token): un texto que el servidor firma y le entrega al cliente al autenticarse. En cada petición siguiente, el cliente lo muestra y el servidor verifica la firma para dejarlo pasar.

Es la manilla de un concierto: muestras tu cédula una vez en la entrada (login) y te ponen una manilla firmada. Adentro ya no muestras la cédula en cada puerta, solo la manilla.

Un JWT es un texto largo con tres partes separadas por puntos:

estructura de un token (header.payload.firma) 
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiJsYXVyYSIsInJvbCI6IkFETUlOIn0.dBjftJeZ4CVP-mB92K27u...

Parte 1 (Header): qué algoritmo firma el token. Parte 2 (Payload): los datos, ej. "el usuario es laura, rol ADMIN". No es secreto, cualquiera lo lee. Parte 3 (Firma): el sello de seguridad, calculado con una clave secreta que solo el servidor conoce.

Si el contenido del token lo puede leer cualquiera, ¿no es peligroso? ¿Cómo evitamos que alguien se invente un token diciendo que es ADMIN?
▸ Ver explicación
El token no se esconde, se firma. Cualquiera puede leer que dice "rol ADMIN", pero nadie puede falsificarlo sin la clave secreta del servidor. Si alguien cambia una letra del payload, la firma ya no cuadra y el servidor lo rechaza. Es como un billete: puedes verlo, pero no puedes imprimir uno falso que pase la prueba de autenticidad.
08 · IMPLEMENTACIÓN

🏭 El JwtService: crear y validar tokens

Este es el archivo más importante de la clase. El JwtService es la fábrica de tokens: sabe crear un token cuando alguien entra, y leer y validar un token cuando alguien vuelve.

Atención: cambio de sintaxis

La librería jjwt cambió en la versión 0.12.x. Si ves código viejo con setSubject(...) o parserBuilder(), no compila aquí. La forma nueva usa subject(...), verifyWith(...), parseSignedClaims(...) y Jwts.SIG.HS256. Usa el de esta guía.

Primero, la clave secreta va en application.properties, junto al tiempo de expiración.

src/main/resources/application.properties · agregar al final 
# Clave secreta para firmar los JWT (en produccion iria en variable de entorno)
jwt.secret=EstaEsUnaClaveSecretaMuyLargaParaVetCare2026SeguridadJWT
# Duracion del token en milisegundos (aqui, 24 horas)
jwt.expiration=86400000
Ojo

La clave debe ser larga (mínimo 32 caracteres para HS256). Si es corta, jjwt lanza un error al arrancar.

Ahora el servicio completo. Léelo por partes: la clave, generar el token, y leer/validar.

src/main/java/com/devsenior/vetcare/service/JwtService.java 
package com.devsenior.vetcare.service;

import io.jsonwebtoken.Claims;
import io.jsonwebtoken.Jwts;
import io.jsonwebtoken.security.Keys;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.stereotype.Service;

import javax.crypto.SecretKey;
import java.nio.charset.StandardCharsets;
import java.util.Date;

@Service
public class JwtService {

    @Value("${jwt.secret}")
    private String secret;

    @Value("${jwt.expiration}")
    private long expiration;

    // Convierte el texto secreto en la llave que usa jjwt para firmar
    private SecretKey getKey() {
        return Keys.hmacShaKeyFor(secret.getBytes(StandardCharsets.UTF_8));
    }

    // Crea un token con el username, el rol, y su fecha de vencimiento
    public String generarToken(UserDetails userDetails, String rol) {
        return Jwts.builder()
                .subject(userDetails.getUsername())
                .claim("rol", rol)
                .issuedAt(new Date())
                .expiration(new Date(System.currentTimeMillis() + expiration))
                .signWith(getKey())
                .compact();
    }

    // Saca el username que viaja dentro del token
    public String extraerUsername(String token) {
        return extraerClaims(token).getSubject();
    }

    // Verifica firma + vencimiento leyendo el contenido del token
    private Claims extraerClaims(String token) {
        return Jwts.parser()
                .verifyWith(getKey())
                .build()
                .parseSignedClaims(token)
                .getPayload();
    }

    // El token es valido si el username coincide y no esta vencido
    public boolean esValido(String token, UserDetails userDetails) {
        String username = extraerUsername(token);
        boolean vencido = extraerClaims(token).getExpiration().before(new Date());
        return username.equals(userDetails.getUsername()) && !vencido;
    }
}
En esValido verificamos dos cosas: que el username coincida Y que no esté vencido. ¿Por qué no basta con solo verificar la firma?
▸ Ver explicación
La firma prueba que el token es auténtico (lo hicimos nosotros), pero no que siga siendo vigente ni del usuario correcto. Un token robado y vencido no debe entrar: por eso revisamos la expiración. Y confirmamos que el username corresponda al usuario. Autenticidad, vigencia e identidad: las tres.
09 · PUENTE

👥 UserDetailsService: conectar tus usuarios con Spring Security

Spring Security no conoce tu tabla usuarios. Trabaja con su propio "molde" de usuario, llamado UserDetails. Necesitas un traductor: una clase que, dado un username, busque en TU base y le entregue a Spring un UserDetails que entienda.

UserDetailsService: la interface de Spring Security cuyo método loadUserByUsername carga un usuario desde donde tú quieras (tu base) y lo entrega en el formato que Spring maneja.

Es como un intérprete de idiomas: tu base habla "español" (entidad Usuario) y Spring habla "inglés" (UserDetails); el traductor los pone de acuerdo.

src/main/java/com/devsenior/vetcare/service/UsuarioDetailsService.java 
package com.devsenior.vetcare.service;

import com.devsenior.vetcare.model.Usuario;
import com.devsenior.vetcare.repository.UsuarioRepository;
import org.springframework.security.core.authority.SimpleGrantedAuthority;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.core.userdetails.UsernameNotFoundException;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class UsuarioDetailsService implements UserDetailsService {

    private final UsuarioRepository usuarioRepository;

    public UsuarioDetailsService(UsuarioRepository usuarioRepository) {
        this.usuarioRepository = usuarioRepository;
    }

    @Override
    public UserDetails loadUserByUsername(String username) {
        Usuario usuario = usuarioRepository.findByUsername(username)
                .orElseThrow(() -> new UsernameNotFoundException(
                        "Usuario no encontrado: " + username));

        return new User(
                usuario.getUsername(),
                usuario.getPassword(),   // ya viene encriptada de la base
                List.of(new SimpleGrantedAuthority("ROLE_" + usuario.getRol().name()))
        );
    }
}
¿Por qué le agregamos el prefijo ROLE_ al rol (queda ROLE_ADMIN) en vez de dejarlo como ADMIN a secas?
▸ Ver explicación
Spring Security tiene una convención: internamente espera que los roles empiecen con ROLE_. Cuando más adelante escribas hasRole("ADMIN"), Spring le agrega solito el ROLE_ y busca ROLE_ADMIN. Si no sigues la convención al guardar la autoridad, los permisos no cuadran y nada funciona.
10 · IMPLEMENTACIÓN

🚦 El filtro JWT: el portero de cada petición

Necesitas algo que intercepte CADA petición que llega, mire si trae un token, lo valide, y si es correcto le diga a Spring "este usuario ya está identificado". Ese portero es un filtro.

OncePerRequestFilter: un filtro de Spring que se ejecuta exactamente una vez por cada petición HTTP, ideal para revisar el token antes de que la petición llegue a tu controlador.

Es el portero de una discoteca: revisa la manilla de cada persona que entra, una sola vez, en la puerta.

Su trabajo: mira si viene el header Authorization con un token (Bearer xxxxx), saca el username, valida, y si todo cuadra marca al usuario como autenticado para esa petición.

src/main/java/com/devsenior/vetcare/config/JwtFilter.java 
package com.devsenior.vetcare.config;

import com.devsenior.vetcare.service.JwtService;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.context.SecurityContextHolder;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.web.authentication.WebAuthenticationDetailsSource;
import org.springframework.stereotype.Component;
import org.springframework.web.filter.OncePerRequestFilter;

import java.io.IOException;

@Component
public class JwtFilter extends OncePerRequestFilter {

    private final JwtService jwtService;
    private final UserDetailsService userDetailsService;

    public JwtFilter(JwtService jwtService, UserDetailsService userDetailsService) {
        this.jwtService = jwtService;
        this.userDetailsService = userDetailsService;
    }

    @Override
    protected void doFilterInternal(HttpServletRequest request,
                                    HttpServletResponse response,
                                    FilterChain filterChain)
            throws ServletException, IOException {

        String header = request.getHeader("Authorization");

        // Si no hay header o no empieza con "Bearer ", seguimos sin autenticar
        if (header == null || !header.startsWith("Bearer ")) {
            filterChain.doFilter(request, response);
            return;
        }

        String token = header.substring(7);          // quita "Bearer "
        String username = jwtService.extraerUsername(token);

        if (username != null
                && SecurityContextHolder.getContext().getAuthentication() == null) {

            UserDetails userDetails = userDetailsService.loadUserByUsername(username);

            if (jwtService.esValido(token, userDetails)) {
                UsernamePasswordAuthenticationToken auth =
                        new UsernamePasswordAuthenticationToken(
                                userDetails, null, userDetails.getAuthorities());
                auth.setDetails(new WebAuthenticationDetailsSource().buildDetails(request));
                SecurityContextHolder.getContext().setAuthentication(auth); // autenticado
            }
        }

        filterChain.doFilter(request, response); // deja seguir la peticion
    }
}
Si una petición NO trae token (por ejemplo, alguien pidiendo el login), el filtro la deja pasar igual. ¿Eso no es un hueco de seguridad?
▸ Ver explicación
No, y aquí está la clave: el filtro no bloquea, solo identifica si puede. La decisión de bloquear la toma después la SecurityConfig según la ruta. Si la petición era pública (como el login), pasa. Si era protegida y llegó sin autenticar, Spring la frena más adelante. Separar responsabilidades: el filtro identifica, la config autoriza.
11 · CONFIGURACIÓN

🛡️ La SecurityConfig completa

Vuelves a la SecurityConfig (donde estaba solo el PasswordEncoder) y le agregas el cerebro: la cadena de filtros de seguridad. Aquí decides qué rutas son públicas, cuáles exigen token, que no usas sesiones, y dónde se inserta tu filtro JWT.

Cambio vs. tutoriales viejos

En Spring Security 6 ya no existe WebSecurityConfigurerAdapter. Ahora todo se configura con un @Bean que devuelve un SecurityFilterChain.

src/main/java/com/devsenior/vetcare/config/SecurityConfig.java 
package com.devsenior.vetcare.config;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.dao.DaoAuthenticationProvider;
import org.springframework.security.config.annotation.authentication.configuration.AuthenticationConfiguration;
import org.springframework.security.config.annotation.method.configuration.EnableMethodSecurity;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.http.SessionCreationPolicy;
import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.crypto.bcrypt.BCryptPasswordEncoder;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.security.web.SecurityFilterChain;
import org.springframework.security.web.authentication.UsernamePasswordAuthenticationFilter;

@Configuration
@EnableWebSecurity
@EnableMethodSecurity   // habilita @PreAuthorize (roles por metodo)
public class SecurityConfig {

    private final JwtFilter jwtFilter;
    private final UserDetailsService userDetailsService;

    public SecurityConfig(JwtFilter jwtFilter,
                          UserDetailsService userDetailsService) {
        this.jwtFilter = jwtFilter;
        this.userDetailsService = userDetailsService;
    }

    @Bean
    public PasswordEncoder passwordEncoder() {
        return new BCryptPasswordEncoder();
    }

    // Provee el modo de autenticar: usa nuestro UserDetailsService + BCrypt
    @Bean
    public DaoAuthenticationProvider authenticationProvider() {
        DaoAuthenticationProvider provider = new DaoAuthenticationProvider();
        provider.setUserDetailsService(userDetailsService);
        provider.setPasswordEncoder(passwordEncoder());
        return provider;
    }

    // El AuthenticationManager lo usa el login para verificar credenciales
    @Bean
    public AuthenticationManager authenticationManager(
            AuthenticationConfiguration config) throws Exception {
        return config.getAuthenticationManager();
    }

    // La cadena de seguridad: que se protege y que no
    @Bean
    public SecurityFilterChain securityFilterChain(HttpSecurity http) throws Exception {
        http
            .csrf(csrf -> csrf.disable())
            .authorizeHttpRequests(auth -> auth
                .requestMatchers("/api/auth/**").permitAll()
                .requestMatchers(
                        "/swagger-ui/**",
                        "/swagger-ui.html",
                        "/v3/api-docs/**").permitAll()
                .anyRequest().authenticated()
            )
            .sessionManagement(session -> session
                .sessionCreationPolicy(SessionCreationPolicy.STATELESS))
            .authenticationProvider(authenticationProvider())
            .addFilterBefore(jwtFilter,
                    UsernamePasswordAuthenticationFilter.class);

        return http.build();
    }
}

Qué hace cada línea clave: csrf.disable() porque somos API con token, no formularios con sesión. permitAll() en /api/auth/** y Swagger: públicos. anyRequest().authenticated(): todo lo demás exige token. STATELESS: sin sesiones, cada petición se identifica sola. addFilterBefore: tu filtro lee el token primero.

¿Por qué las rutas de login y registro tienen que ser públicas obligatoriamente?
▸ Ver explicación
Porque son la puerta de entrada. Para conseguir un token, primero hay que hacer login. Pero para hacer login se necesita poder llamar al login sin token. Si lo protegieras exigiendo token, sería el candado con la llave adentro: nadie podría entrar nunca.
12 · IMPLEMENTACIÓN

🔑 Completar el login con token real

Ya existe el JwtService y toda la maquinaria. Vuelves al AuthServiceImpl y lo completas: verifica credenciales con el AuthenticationManager y, si son correctas, genera y devuelve el token.

src/main/java/com/devsenior/vetcare/service/impl/AuthServiceImpl.java 
package com.devsenior.vetcare.service.impl;

import com.devsenior.vetcare.dto.AuthResponse;
import com.devsenior.vetcare.dto.LoginRequest;
import com.devsenior.vetcare.dto.RegistroRequest;
import com.devsenior.vetcare.model.Usuario;
import com.devsenior.vetcare.repository.UsuarioRepository;
import com.devsenior.vetcare.service.AuthService;
import com.devsenior.vetcare.service.JwtService;
import org.springframework.security.authentication.AuthenticationManager;
import org.springframework.security.authentication.UsernamePasswordAuthenticationToken;
import org.springframework.security.core.userdetails.User;
import org.springframework.security.core.userdetails.UserDetails;
import org.springframework.security.crypto.password.PasswordEncoder;
import org.springframework.stereotype.Service;

import java.util.List;

@Service
public class AuthServiceImpl implements AuthService {

    private final UsuarioRepository usuarioRepository;
    private final PasswordEncoder passwordEncoder;
    private final JwtService jwtService;
    private final AuthenticationManager authenticationManager;

    public AuthServiceImpl(UsuarioRepository usuarioRepository,
                           PasswordEncoder passwordEncoder,
                           JwtService jwtService,
                           AuthenticationManager authenticationManager) {
        this.usuarioRepository = usuarioRepository;
        this.passwordEncoder = passwordEncoder;
        this.jwtService = jwtService;
        this.authenticationManager = authenticationManager;
    }

    @Override
    public AuthResponse registrar(RegistroRequest request) {
        if (usuarioRepository.findByUsername(request.username()).isPresent()) {
            throw new RuntimeException("El username ya esta registrado");
        }

        Usuario usuario = new Usuario();
        usuario.setUsername(request.username());
        usuario.setPassword(passwordEncoder.encode(request.password()));
        usuario.setRol(request.rol());
        usuarioRepository.save(usuario);

        UserDetails userDetails = new User(usuario.getUsername(), usuario.getPassword(), List.of());
        String token = jwtService.generarToken(userDetails, usuario.getRol().name());
        return new AuthResponse(token);
    }

    @Override
    public AuthResponse login(LoginRequest request) {
        // 1. Verifica username + password (lanza excepcion si son incorrectos)
        authenticationManager.authenticate(
                new UsernamePasswordAuthenticationToken(
                        request.username(), request.password()));

        // 2. Si paso, busca el usuario para leer su rol
        Usuario usuario = usuarioRepository.findByUsername(request.username())
                .orElseThrow(() -> new RuntimeException("Usuario no encontrado"));

        // 3. Genera el token con su rol
        UserDetails userDetails = new User(usuario.getUsername(), usuario.getPassword(), List.of());
        String token = jwtService.generarToken(userDetails, usuario.getRol().name());
        return new AuthResponse(token);
    }
}

14 · AUTORIZACIÓN

👮 Roles en acción: que USER no pueda borrar

Hasta ahora, cualquier usuario autenticado puede hacer todo. Pero eso no es realista: una recepcionista (USER) debería consultar y crear, pero no borrar. Borrar es cosa del ADMIN.

@PreAuthorize: anotación que protege un método concreto según una condición de seguridad. @PreAuthorize("hasRole('ADMIN')") significa "solo un ADMIN puede ejecutar este método".

Es el letrero de "solo personal autorizado" en una puerta: no importa que ya estés dentro del edificio, esa sala en particular tiene su propia restricción.

Regla de negocio de VetCare

USER consulta y crea. ADMIN además actualiza y borra. Memorízala.

Primero configura Swagger para que muestre el botón Authorize (el candadito), y así pueda mandar el token.

15 · CIERRE PRO

🧹 Errores limpios: el 404 con @ControllerAdvice

¿Recuerdas que al buscar un id inexistente salía un feo error 500? Hoy lo conviertes en un 404 elegante. Y de paso manejas los errores de seguridad (403) y de validación (400).

@ControllerAdvice / @RestControllerAdvice: una clase que atrapa las excepciones de toda la API en un solo lugar y las convierte en respuestas limpias, en vez de manejar errores en cada controlador.

Es como el área de reclamos central de una empresa: en vez de que cada mostrador improvise su respuesta, todos los problemas llegan a un mismo lugar que responde de forma consistente.

Primero un DTO simple para el error:

src/main/java/com/devsenior/vetcare/dto/ErrorResponse.java

        int codigo,
        String mensaje,
        LocalDateTime fecha
) {}

Y el manejador global. Cada @ExceptionHandler atrapa un tipo de error y devuelve la respuesta adecuada:

src/main/java/com/devsenior/vetcare/exception/ManejadorGlobalExcepciones.java 
package com.devsenior.vetcare.exception;

import com.devsenior.vetcare.dto.ErrorResponse;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.security.access.AccessDeniedException;
import org.springframework.web.bind.MethodArgumentNotValidException;
import org.springframework.web.bind.annotation.ExceptionHandler;
import org.springframework.web.bind.annotation.RestControllerAdvice;

import java.time.LocalDateTime;

@RestControllerAdvice
public class ManejadorGlobalExcepciones {

    // 404: recurso no encontrado
    @ExceptionHandler(RecursoNoEncontradoException.class)
    public ResponseEntity<ErrorResponse> noEncontrado(RecursoNoEncontradoException ex) {
        ErrorResponse error = new ErrorResponse(
                HttpStatus.NOT_FOUND.value(),
                ex.getMessage(),
                LocalDateTime.now());
        return ResponseEntity.status(HttpStatus.NOT_FOUND).body(error);
    }

    // 403: sin permiso (USER intentando borrar)
    @ExceptionHandler(AccessDeniedException.class)
    public ResponseEntity<ErrorResponse> accesoDenegado(AccessDeniedException ex) {
        ErrorResponse error = new ErrorResponse(
                HttpStatus.FORBIDDEN.value(),
                "No tienes permiso para realizar esta accion",
                LocalDateTime.now());
        return ResponseEntity.status(HttpStatus.FORBIDDEN).body(error);
    }

    // 400: fallo una validacion de @Valid
    @ExceptionHandler(MethodArgumentNotValidException.class)
    public ResponseEntity<ErrorResponse> validacion(MethodArgumentNotValidException ex) {
        String mensaje = ex.getBindingResult().getFieldErrors().stream()
                .findFirst()
                .map(e -> e.getField() + ": " + e.getDefaultMessage())
                .orElse("Error de validacion");
        ErrorResponse error = new ErrorResponse(
                HttpStatus.BAD_REQUEST.value(),
                mensaje,
                LocalDateTime.now());
        return ResponseEntity.status(HttpStatus.BAD_REQUEST).body(error);
    }
}

¿Por qué es mejor tener los errores centralizados en UNA clase en vez de un try/catch en cada método de cada controlador?
▸ Ver explicación
Por dos razones. Consistencia: todos los "no encontrado" de toda la API responden igual. Mantenimiento: si mañana cambias el formato del error, lo cambias en un solo lugar y aplica a todo. Con try/catch repartidos tendrías que tocar decenas de métodos. Centralizar es la buena práctica (principio DRY: no te repitas).
