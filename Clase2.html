Herramienta profesional

🛠️Swagger: documentación que nunca miente

El navegador solo sabe hacer GET. Para probar POST, PUT y DELETE sin instalar Postman, incrustamos Swagger UI dentro de la propia aplicación.

Swagger lee los controladores y genera una página interactiva donde cada endpoint es un botón ejecutable. Es el estándar de la industria para documentar y probar una API.

💭¿Por qué preferimos una herramienta que se genera sola desde el código, en lugar de documentar la API a mano?
Porque un documento manual se desactualiza apenas cambia un endpoint. Swagger lee el código en vivo: si agregas un endpoint, aparece solo; si cambia un parámetro, se refleja al instante. La documentación nunca miente porque es el código mismo.

Diseño de API

🎁DTOs: el contrato limpio de la API

Hasta ahora usábamos @JsonIgnore como parche para evitar la recursión infinita. Hoy vemos la solución profesional.

Un DTO (Data Transfer Object) es un objeto simple que representa exactamente los datos que viajan por la API, ni más ni menos. La entidad vive puertas adentro (habla con la base); el DTO es lo que sale a la calle.

💭Al registrar un dueño, ¿el cliente de la API debería enviar el id? ¿Y la lista completa de mascotas en el mismo formulario?
No. El id lo genera la base, no el cliente. Y las mascotas se registran por su propio endpoint, no dentro del dueño. Si expones la entidad tal cual, aceptas datos que no deberías y filtras estructura interna. El DTO define un contrato limpio: "para crear un dueño, mándame solo estos campos".
💼 Vida real La entidad es tu historia clínica completa en el hospital. El DTO es el formulario de admisión: solo piden nombre, documento y teléfono. Cada cosa expone lo justo.

📐 Dos tipos de DTO

DTODirecciónPara qué sirve
Requestentra (cliente → API)define qué campos acepto al crear/actualizar
Responsesale (API → cliente)define qué campos devuelvo, sin recursión
Herramienta del lenguaje

🧱¿Qué es un record?

Para escribir los DTOs usamos una forma corta de declarar una clase cuyo único propósito es transportar datos: una cajita con campos, sin lógica adentro.

🔍 Una línea, cuatro cosas gratis

Cuando escribimos esto:

public record DuenoResponse(Long id, String nombre) {}

Java genera, por detrás y automáticamente:

🏗️ Constructor

Recibe id y nombre.

📖 Lectores

Métodos id() y nombre() — sin el prefijo get.

⚖️ equals / hashCode / toString

Ya implementados, sin escribirlos.

🔒 Inmutabilidad

Una vez creado el objeto, sus valores no cambian.

🆚 Entidad vs. DTO

Entidad (clase + Lombok)DTO (record)
Para quéMapear una tabla, vive con JPATransportar datos por la API
Leer un campodueno.getNombre()request.nombre()
¿Cambian sus datos?Sí, tiene settersNo, es inmutable
Palabra claveclassrecord
💭Si record es tan corto y práctico, ¿por qué no reemplazamos también las entidades por records?
Porque JPA necesita modificar la entidad (asignarle el id que genera la base, cambiar campos) y necesita un constructor vacío. Un record es inmutable y no tiene constructor vacío, así que no sirve como entidad. En cambio es perfecto para un DTO, que solo lleva datos de ida y vuelta.
🔑

Regla simple: entidad → class con Lombok. DTO → record.

📄 dto/DuenoResponse.java
package com.devsenior.vetcare.dto; public record DuenoResponse( Long id, String nombre, String apellido, String documento, String telefono, String email ) {}
💭¿Por qué el DuenoResponse sí lleva id pero el DuenoRequest no?
El id lo genera la base de datos, no el cliente. Al crear (Request) el dueño todavía no tiene id. Al responder (Response) ya existe en la base y el cliente lo necesita para futuras operaciones. Cada DTO expone solo lo que corresponde a su momento.

🧩 Service: la conversión vive aquí

🔑

Decisión de diseño: la conversión entre entidad y DTO la hace el propio ServiceImpl, con dos métodos privados (toEntity y toResponse). No creamos una clase aparte: convertir es parte del trabajo del servicio, respetando la arquitectura de 4 capas (Interface → Repository → ServiceImpl → Controller).

📄 service/DuenoService.java
public interface DuenoService { List<DuenoResponse> listarTodos(); DuenoResponse buscarPorId(Long id); DuenoResponse crear(DuenoRequest request); DuenoResponse actualizar(Long id, DuenoRequest request); void eliminar(Long id); }

💭En actualizar, ¿por qué primero busco el dueño en la base en vez de crear uno nuevo con el id y guardarlo directo?
Si creo uno nuevo, piso los campos que no venían en el request (por ejemplo, dejaría sus mascotas huérfanas o borraría datos). Al traer el existente y modificar solo sus campos, conservo lo demás intacto. Además, si el id no existe, me entero y lanzo el 404. Es la forma segura de actualizar.

💭¿Por qué crear devuelve 201 y no simplemente 200? ¿Y por qué eliminar devuelve 204 (sin contenido)?
Cada código cuenta una historia al cliente: 201 Created dice "creé algo nuevo" — más preciso que un genérico 200. 204 No Content dice "lo borré, no tengo nada que devolverte". Usar el código correcto es parte de diseñar una API REST profesional: el cliente sabe qué pasó solo por el número.

Segunda entidad · con relación

🐶CRUD de Mascota: la primera relación

Una mascota nunca existe sola: siempre pertenece a un dueño. Aquí aparece el reto real de esta clase: manejar relaciones al recibir datos.

💭Para registrar la mascota de Juan, ¿hay que volver a escribir todo el nombre, documento y teléfono de Juan?
No. Solo se necesita el id de Juan. Juan ya está en la base. En el request de la mascota se manda duenoId: 1, y el backend busca a Juan y lo asocia. No se repiten datos: se referencia por id. Así funcionan las relaciones en las APIs reales.

💭¿Qué pasaría en la vida real si se permitiera registrar una mascota con un duenoId que no existe?
Tendríamos una mascota fantasma: sin dueño real, imposible de contactar, rompiendo la integridad del sistema. En la clínica sería un perro registrado sin saber de quién es. Por eso se valida la existencia del dueño antes de guardar — esa es lógica de negocio, y por eso vive en el service.

📅CRUD de Cita: dos relaciones a la vez

La Cita conecta una mascota (quién se atiende) y un veterinario (quién atiende): dos relaciones @ManyToOne al mismo tiempo.

💭Para agendar una cita, ¿qué dos cosas mínimas hay que referenciar, además de la fecha y el motivo?
La mascota que se atiende y el veterinario que la atenderá. Sin esos dos, la cita no tiene sentido de negocio. Por eso el Request de Cita lleva mascotaId y veterinarioId, y el service valida que ambos existan antes de agendar.

💭El service de Cita repite el mismo patrón que el de Mascota, pero validando dos relaciones en vez de una. ¿Por qué es buena señal?

❓ Preguntas frecuentes

🔹 ¿Por qué usamos record para los DTOs y no para las entidades?
El record es inmutable y no tiene constructor vacío; JPA necesita ambas cosas para manejar la entidad. Por eso: entidad → clase con Lombok; DTO → record.
🔹 ¿Por qué la conversión DTO ↔ entidad va dentro del ServiceImpl y no en una clase aparte?
Convertir es parte del trabajo del servicio, así se mantiene la arquitectura de 4 capas sin agregar carpetas nuevas. Los métodos toEntity/toResponse son privados: solo los usa ese servicio.
🔹 Si borro un dueño que tiene mascotas, ¿qué pasa?
Por el cascade = CascadeType.ALL y orphanRemoval definidos en la Clase 1, se borran también sus mascotas (y por cascada, sus citas). Ese es el comportamiento definido para VetCare.
🔹 ¿Por qué al buscar un id inexistente sale error 500 y no 404?
Porque todavía no existe el manejador global. Hoy se lanza la excepción; en la Clase 3 se atrapa con @ControllerAdvice y se convierte en un 404 elegante.
🔹 ¿El id en Swagger lo escribo yo?
No para crear — la base lo genera. Solo se escribe en las rutas con {id} (buscar, actualizar, eliminar), usando un id que ya exista.
